# DirectShow 曝光上限与黑帧复核

执行时间：2026-10-02（Asia/Shanghai）。办公室控制服务：`100.103.31.118:8770`；文件服务：`100.103.31.118:8765`。设备为单路并排双目，输入 `3840×1080`，左右目各 `1920×1080`，OpenCV backend `700`（DirectShow）。

## 结论

当前设备在这条 DirectShow、并排 MJPG 模式下，实测能稳定回读的最长手动曝光是 **250 ms（约 1/4 秒）**。请求 `500 ms`、`1000 ms` 或 `2000 ms` 时，驱动仍回读原生 `-2`，即 `250 ms`；这些请求没有真正生效。应用允许的 2000 ms 只是请求上限，不是设备能力上限。

黑帧也不是单纯因为快门不够长：在 `125 ms` 和 `250 ms` 回读成功时，左右目仍为近零亮度；请求 `1000 ms`、`2000 ms` 的 20 秒连续预热以及 AUTO 的 20 秒连续预热都没有得到 3 帧连续可用图像。此前同一设备的现场复核曾出现手动短快门“首帧亮、随后变黑”，重开后显式 AUTO 可恢复 8/8 对。这说明问题集中在 DirectShow/相机驱动的曝光模式切换或流状态，尚不能归因于识别算法。

## 驱动判断的边界

Windows `IAMCameraControl` 的曝光值采用以 2 为底的秒数对数；设备可以只实现其中一部分档位。当前 Python/OpenCV 接口只能看到 `CAP_PROP_EXPOSURE` 的请求和回读，不能直接读取 DirectShow `GetRange` 的最小值、最大值和步长，因此本报告的 250 ms 是“现场实测上限”，不是驱动声明的完整范围。

OpenCV 的 DirectShow 实现为 `CAP_PROP_AUTO_EXPOSURE` 传入控制标志，但普通 `CAP_PROP_EXPOSURE` 设置路径没有把 `CameraControl_Flags_Manual` 作为独立参数传给驱动；一些相机在这种切换顺序下会接受 API 调用却输出黑帧。需要用原厂工具或原生 DirectShow 控制接口，对照检查 `GetRange/Set`、增益和流模式，不能仅凭 `set()` 返回 `True` 宣称曝光已经生效。
